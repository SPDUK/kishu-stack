# Kishu setup

Walk the user through the choices needed to use Kishu in this host. Reuse choices already given and existing configuration. A setup request authorizes setup, but it does not tell you which personal defaults the user wants.

1. Identify the active harness and Kishu entrypoints from the installed skill inventory. Read the applicable adapter if needed. Report a missing capability only when it affects this setup; do not perform a broad environment audit.
2. Use the inherited [model setup workflow](../lib/pstack/skills/setup-pstack/SKILL.md). Show existing choices if present, with a choice to keep or customize them. For a new setup, offer inherited models or a supported per-role mapping and reasoning target. Keep model IDs and effort separate on Codex. Apply explicit choices without asking for the same approval again.
3. Offer **manual activation** or **always-on Kishu**. If always-on is chosen and scope is not already clear, ask whether it applies to this project or all their chats in this harness. Preserve the host's existing instructions and use a single `<!-- kishu:begin -->` / `<!-- kishu:end -->` block. The block should say to use the **installed Kishu mode skill** from the host's skill inventory (Codex `kishu:kishu-mode`), follow its router, and prioritize current user/project instructions. Do not point the rule at a versioned plugin cache or copy the router into it. For a Cursor `.mdc` rule, preserve existing frontmatter and set `alwaysApply: true`. If the source checkout is available, `python scripts/kishu.py activate --harness <host> --instructions <chosen-file>` implements this block.
4. Read back any saved settings and report what is active, where preferences were saved, and how to invoke Kishu next time. Explain that delegated model preferences do not switch the main chat's model. A new chat may be needed to refresh the host's skill inventory.

Do not add a design questionnaire, project-verification generator, formal verification, or unrelated plugin installs to this walkthrough. The user can ask for those separately. Existing instructions that point at an older absolute Kishu path can be updated within their marked Kishu block when always-on setup is requested.
